# Plan the migration

1. Use `gems status` to confirm the current phase is `planning`. Read the accepted setup and diagnosis and the installed engine profiles. Delegate strategy, scope, dependencies, criteria, and alternatives to the Migration Planner. Resolve blocking decisions with the developer and use selectable options when available.
2. Write `migration-plan.json` in the configured output folder using `../../templates/plan.json`. Assign a revision and identify every destination file each unit may modify. Use destination-relative file paths. Give each unit's required technical checks IDs and reproducible procedures. Make the expected result and method explicit for each equivalence criterion, including its phase, mandatory status, and tolerance when applicable. Use `null` for tolerance when the method has no numerical threshold.
3. Present the proposed revision and use `*approve`. Upon explicit approval, run `gems approve --revision <id> --actor <developer>`. Run `gems validate` and then `gems advance --phase planning --actor <name>` to record the handoff. When inputs change, use `gems replan --reason <reason> --actor <name>` if the current contract requires a return to planning or diagnosis.
